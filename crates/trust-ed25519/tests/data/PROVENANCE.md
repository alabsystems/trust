# Provenance of the vendored Ed25519 test vectors

This directory holds two files of vectors and they have **different
provenance**, which is the first thing to know about them:

| File | Provenance | Meaning |
|---|---|---|
| `rfc8032_7_1.txt` | **PUBLISHED** | Transcribed mechanically from the RFC 8032 text. Authority is the RFC. |
| `edge_vectors.txt` | **DERIVED** | Computed by `derive_edge_vectors.py`, an independent Python implementation. Authority is that script plus the RFC sections it cites. |

Neither was typed by hand, and **neither was produced by this crate or by the
incumbent**. That last distinction is the whole point: a known-answer test
whose answers came from the implementation under test is not a test.

## `rfc8032_7_1.txt` — PUBLISHED

| | |
|---|---|
| Source | RFC 8032, *Edwards-Curve Digital Signature Algorithm (EdDSA)*, S. Josefsson & I. Liusvaara, January 2017 — **§7.1, "Test Vectors for Ed25519"** |
| Retrieved from | `https://www.rfc-editor.org/rfc/rfc8032.txt` |
| SHA-256 of the retrieved RFC text | `ed63657ff389301282b169b0abde9b5dd2c7e4d524fdfa5da6ff3094fc93c4c3` |
| Retrieved | 2026-08-22 |
| Extracted by | `extract_rfc8032.py`, in this directory |
| Records | 5 — TEST 1, TEST 2, TEST 3, TEST 1024, TEST SHA(abc) |
| SHA-256 of `rfc8032_7_1.txt` | `d90a18cf22bbc8fb94640908711c15918edffac7e0981d83406d13bd5dfa8142` |

RFC 8032 §7.1 states its own upstream: the vectors "are taken from
[ED25519-TEST-VECTORS] [...] and [ED25519-LIBGCRYPT-TEST-VECTORS]".

### Why there is an extractor script rather than a transcription

Transcribing 128-hex-character signatures by hand is exactly the step that
introduces a wrong constant, and a *wrong* known-answer test is worse than no
test: it either fails for the wrong reason or, if someone "fixes" it against
the implementation's own output, silently converts a PUBLISHED vector into a
DERIVED one and the gate stops being a gate.

`extract_rfc8032.py` reads the RFC text, walks §7.1 line by line, strips the
page furniture (form feeds, running headers, the `Josefsson & Liusvaara`
footer), reassembles each field from its 32-hex-character continuation lines,
and **asserts the lengths**: 64 hex for each key, 128 for each signature, and
`2 x` the byte count the RFC prints in the `MESSAGE (length N bytes)` label. A
dropped or duplicated line therefore fails extraction rather than producing a
plausible-looking wrong vector.

This was not a theoretical concern. The first attempt at this file fetched the
RFC through a summarising HTTP tool, whose output corrupted TEST 2's signature
in two places — a `0` rendered as the letter `O`, and four hex digits changed
(`...5f642540` became `...5f64254a`). Both would have been caught by the
implementation failing the test, but only after the failure had been
misattributed. The lengths-checked extractor over the raw octets is the fix.

### Regenerating

```sh
curl -sSo rfc8032.txt https://www.rfc-editor.org/rfc/rfc8032.txt
shasum -a 256 rfc8032.txt          # must match the table above
python3 extract_rfc8032.py rfc8032.txt vectors.json
```

`extract_rfc8032.py` prints the source digest and one line per vector. The
`.txt` in this directory is the same data flattened to `name|sk|pk|msg|sig`.

## `edge_vectors.txt` — DERIVED

RFC 8032 §7.1 publishes five *valid* triples and nothing else. It publishes no
vector for any case a verifier is likely to get **wrong** — a non-canonical
`y`, an encoding that is not a curve point, a malleated `S`, a small-order
key. Those vectors do not exist in published form, so this file derives them.

| | |
|---|---|
| Generated by | `derive_edge_vectors.py`, in this directory |
| Inputs | RFC 8032 §5.1 Table 1 parameters; `rfc8032_7_1.txt` for the malleation base |
| Records | 19 `noncanonical_y`, 8 `off_curve_y`, 8 `small_order`, 5 `malleated_sig`, 1 `identity_forgery`, 33 `zero_key_zero_sig` |

### Why the derivation is independent of the crate

A derived vector is only worth something if it could disagree with the
implementation it tests. `derive_edge_vectors.py` is built so that it can:

* arithmetic is Python's arbitrary-precision `int`, **not** a 5×51-limb
  representation — a carry-chain defect in `field.rs` cannot be mirrored;
* the group law is the **affine** law of RFC 8032 §5.1.4, **not** the extended
  `add-2008-hwcd-3` the crate uses — a mistranscribed `2d` cannot be mirrored;
* the scalar reduction is Python's `%`, **not** restoring long division — a
  dropped high bit cannot be mirrored.

The script re-derives `d` from `-121665/121666` and checks `[L]B = 0` before
emitting anything, so the parameters are checked against their definitions
rather than assumed.

`src/edwards.rs`'s `eight_torsion_matches_the_derivation` closes the loop: it
re-derives the 8-torsion subgroup *inside this crate*, in limbs and extended
coordinates, and asserts all eight encodings equal the ones in this file. Two
implementations sharing no code agree.

### The records that carry their own non-vacuity proof

Two kinds exist because the obvious version of the test was **measured to be
vacuous or wrong**:

* `malleated_sig` — `(R, S+L)` rather than an arbitrary out-of-range `S`.
  Since `B` has order `L`, `[S+L]B = [S]B`, so it satisfies the §5.1.7 group
  equation exactly as the published signature does and *only* the `0 ≤ S < L`
  range check can reject it. The script evaluates that equation for all five
  vectors and refuses to emit a record unless it holds. An arbitrary
  out-of-range `S` also fails the equation, so it would be rejected by an
  implementation with no range check at all — which is what made the earlier
  version of that test pass under a mutation that deleted the check.
* `zero_key_zero_sig` — a **per-message verdict**, not a constant. The
  all-zeros key is an order-4 point, so the equation reduces to `[k+1]A = 0`
  and holds exactly when `k ≡ 3 (mod 4)`: about a quarter of messages are
  accepted, *correctly*. The first draft of the corresponding test asserted
  blanket rejection and failed on the third message it tried. The script
  emits both the full-equation result and the `k mod 4` shortcut and asserts
  they agree, and refuses a one-sided sample.

### Regenerating

```sh
python3 derive_edge_vectors.py rfc8032_7_1.txt > edge_vectors.txt
```

It prints a summary to stderr and asserts throughout; a failed assertion means
no file, rather than a plausible-looking wrong vector.

## What is NOT here

* **No vector derived from `ed25519-dalek`.** The comparison against the
  incumbent lives in `tests/differential_ed25519.rs`, which computes both
  sides at run time while both crates are in the graph. Nothing derived from
  the incumbent is frozen into a file, because a frozen incumbent-derived
  vector outlives the incumbent and then reads as independent evidence when it
  is not. `edge_vectors.txt` is the file that is *meant* to outlive it.
* **No Ed25519ph or Ed25519ctx vectors** (RFC 8032 §7.2, §7.3). This crate
  implements plain Ed25519 only, which is all `trust-proof-cert` uses.
* **No CCTV / Wycheproof edge-case corpus.** `edge_vectors.txt` now covers the
  low-order and non-canonical classes those corpora are usually pulled in for;
  vendoring them would still add independent authorship, and is the natural
  follow-up when the incumbent leaves.

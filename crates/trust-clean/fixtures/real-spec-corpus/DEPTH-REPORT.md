# Trust verification — TRUE-DEPTH audit (real-spec corpus)

Date: 2026-06-26. Worktree from main HEAD `22e9251b69` (clean pin 379f9c89).
Prebuilt dumping compiler: `build/aarch64-apple-darwin/stage2/bin/trustc`.
Kernel prover: `trust_clean::prove_dump_dir` (the `targo trust prove --kernel`
engine). No prover logic was modified — this is a fixture dir + two measurement
test files only.

The adversarial audit's sharpest finding: *the Trust verification corpus is
spec-free (one-line bodies, zero postconditions), so 18/18 PROVEN and 84%
grounded measure contract-INHABITATION, not verification DEPTH.* This report
tests that head-on and reports the TRUE depth, whatever it is.

---

## STEP 1 — the spec mechanism (what Trust actually supports)

**Finding: Trust DOES support real source-level pre/postconditions — via the
upstream Rust contracts feature, NOT a bare `#[requires]`/`#[ensures]`.**

- Bare `#[requires(...)]` / `#[ensures(...)]` are **rejected** by the prebuilt
  compiler: `error: cannot find attribute 'requires' in this scope`.
- The recognized source syntax is the native Rust contracts attribute macro set,
  gated behind `#![feature(contracts)]`:
  - `#[core::contracts::requires(PRED)]` → precondition
  - `#[core::contracts::ensures(move |ret: &T| PRED)]` → postcondition
    (the closure must be `move` — its captures need `Copy + 'static`).
- Registration: `compiler/rustc_builtin_macros/src/lib.rs:143-146`
  (`contracts_requires` / `contracts_ensures` attr proc-macros);
  desugaring: `compiler/rustc_builtin_macros/src/contracts.rs`;
  feature gate: `compiler/rustc_feature/src/unstable.rs:446`.
- Extraction into the IR: `crates/trust-mir-extract/src/lib.rs`
  `extract_contracts` reads them from `tcx.hir_attrs` (`contract_kind_from_name`
  accepts `requires`/`contracts_requires`/`trust_requires`, etc.), then
  `parse_contract_specs` lowers each into a typed `Formula` placed in the
  dumped `VerifiableFunction.preconditions` / `.postconditions`.

Verified empirically — `#[core::contracts::ensures(move |ret: &i32| *ret >= x)]`
on `id(x)=x` dumps:
```
postconditions: [{"Ge": [{"Var": ["_0","Int"]}, {"Var": ["x","Int"]}]}]
```
So source postconditions ARE first-class, typed Formulas — not only the
auto-generated safety VCs. The auto safety VCs (overflow / bounds / div-by-zero)
are *also* generated by `trust-vcgen` from the body, independent of any contract.

**Why the existing corpora are spec-free anyway:** the checked-in fixture sources
(`fixtures/real-corpus/SOURCE.rs`, `guarded-real-corpus/SOURCE.rs`) carry NO
contract attributes. So the "18/18 PROVEN / high grounding" numbers were measured
on a corpus that exercises only the inhabitation path on trivial contracts. The
audit's premise is correct.

## STEP 2 — the real-spec corpus

`crates/trust-clean/fixtures/real-spec-corpus/SOURCE.rs` — 16 functions across
three honesty groups, dumped with `-Ztrust-dump=mir:<dir>` to 16 `VerifiableFunction`
JSONs (committed alongside).

GROUP A — real POSTCONDITIONS (`#[core::contracts::ensures]`):
- `id_ge`     — `ret >= x`           (identity)
- `inc_gt`    — `ret > x`            (x+1, guarded `x < i32::MAX`)
- `abs_nonneg`— `ret >= 0`           (branch + negation, guarded against MIN)
- `max_ge_a`  — `ret >= a`           (branch-dependent)
- `min_le_a`  — `ret <= a`           (branch-dependent)
- `clamp_lo`  — `ret >= 0`           (saturating-style clamp)

GROUP B — non-trivial AUTO SAFETY VCs, safe for a non-obvious reason:
- `bounded_add`  — `a+b` overflow-free BECAUSE `requires a<1000, b<1000`
- `checked_div`  — `a/b` div-by-0-free BECAUSE `requires b != 0`
- `checked_sub`  — `a-b` underflow-free BECAUSE `requires a >= b`
- `guarded_index`— `s[i]` bounds-safe by an in-body `if i < s.len()` guard
- `guarded_div`  — `a/b` safe by in-body `if b != 0` guard
- `guarded_sub`  — `a-b` safe by in-body `if a >= b` guard

GROUP C — NEGATIVE CONTROLS (an honest verifier MUST NOT discharge these):
- `unsafe_add`   — unguarded `a+b`     → real overflow VC, must fail
- `unsafe_div`   — unguarded `a/b`     → real div-by-zero VC, must fail
- `unsafe_index` — unguarded `s[i]`    → real out-of-bounds VC, must fail
- `false_post`   — `ensures ret > x` on `id` → a FALSE postcondition, must NOT prove

Measurement harnesses (added, not modifying any engine):
- `crates/trust-clean/tests/real_spec_corpus_depth.rs` — full kernel scorecard +
  per-function safety/postcond discharge breakdown.
- `crates/trust-clean/tests/specfree_baseline_compare.rs` — same engine over the
  existing spec-free corpora, for an apples-to-apples comparison.

### Negative controls — behaving correctly (the load-bearing honesty test)

- `unsafe_add`   : overflow VC NOT discharged (0/1).
- `unsafe_index` : bounds VC NOT discharged (0/1).

### THE CAVEAT the audit was right to demand (do not paper over this)

The headline `inhabited = 14/16` **INCLUDES `unsafe_add`, `unsafe_div`,
`unsafe_index`.** That is NOT a soundness bug, but it IS exactly the
inhabitation-vs-depth conflation the audit named:

- "inhabited" = the function's CONTRACT TYPE is inhabited by its return value.
  For a function with NO postcondition, the contract is `Π params → Subtype τ
  (λret. True)` — trivially inhabited. The kernel builds and accepts a real
  inhabitant modulo 3. This is true and sound.
- It says **nothing** about safety. The overflow / div / bounds obligations of
  those same functions are tracked SEPARATELY and are correctly NOT discharged
  (see the breakdown). A reader who takes "14/16 PROVEN" as "14/16 safe+correct"
  is misled; the safety + postcondition discharge columns are the real depth.

### Postcondition depth — the genuinely thin part

Of 6 functions with a real postcondition, only **1 (`inc_gt`)** has its
postcondition discharged by **VC refutation** at the kernel. Three more
(`id_ge`, `max_ge_a`, `min_le_a`) are proven via the **inhabitation path**
(constructive spec-as-type order lemmas) rather than VC refutation — also a real
modulo-3 kernel proof, just a different route. The remaining two:
- `clamp_lo` (`ret >= 0`) — neither route closes (the `if x<0 {0}` branch return
  is outside the inhabitation subset; the postcond VC is not refuted). NOT proven.
- `abs_nonneg` (`ret >= 0`) — the negation branch defeats both routes (NOT
  grounded for inhabitation; 0/2 postcond VCs refuted). NOT proven. The prebuilt
  compiler's own SMT layer also reports `2 proved, 2 failed` here.

So **branch-dependent postconditions over a non-trivial branch (abs, clamp) are
NOT yet provable**; only straight-line or single-comparison order postconditions
close. That is the honest ceiling on postcondition depth today.

and its hardest postconditions don't close.

## HONEST ANSWER — does Trust do real verification depth, or only inhabitation?

Both, in different proportions, and the honest summary is mixed. Trust does
**real, sound, modulo-3 kernel verification** on a genuine fragment: safety VCs
(overflow / underflow / div-by-zero / bounds) that are made safe by a guard or
precondition are reconstructed to actual Clean kernel proofs (28/32 here), the
negative controls are correctly NOT discharged (no vacuous acceptance, including
the FALSE postcondition `false_post`), and zero unsound kernel acceptances
occurred. That is more than inhabitation. **But the depth is thin and narrow:**
only 3/16 functions are FULLY FAITHFUL (the whole-reflection-plus-every-safety-VC
tier), postcondition verification closes only for straight-line / single-order
specs (1 by VC refutation, 3 more by inhabitation) and FAILS on a real
branch-dependent postcondition like `abs >= 0` or `clamp >= 0`, and — crucially —
the flagship `N/N inhabited` headline is a **contract-inhabitation** number that
even counts genuinely-unsafe functions as "proven" because their trivial contract
type is inhabited while their safety obligation is (correctly, separately) left
undischarged. So the audit's core charge stands: the grounding/inhabitation
headline overstates depth, and the true verification depth — the FULLY-FAITHFUL
rate and the postcondition-discharge rate — is single-digit-to-low and bounded to
a straight-line-scalar + single-branch fragment, relative to a trusted MirSem
model and trusted front-end reflection.

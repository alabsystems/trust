# Trust — Vision

Trust is aiming at a self-proving compiler: one program, written in two
languages, proved at the root and compiled into a binary that carries its own
evidence. This document describes that target and how far the implementation has
actually got. Where the two differ, the difference is stated.

- **Author:** Andrew Yates
- **Repo:** <https://github.com/alabsystems/trust>
- **Status:** in development. The verifier is inside the compiler, the two-language
  surface is live, and the Clean kernel is wired as the trust root. The compiler
  does not prove itself — bootstrap runs with verification explicitly disabled;
  what enabling it would cost, and what a green self-build would and would not
  mean, is measured in the internal `SELF_PROOF.md`.
  Daily-driver readiness is machine-local and per-commit: a stage2 sysroot has to
  be freshly built and validated before its reported status may be cited. Strict
  superiority over Rust is unclaimed unless a fresh exact-commit domination
  report passes. Evidence ledger: `docs/DAILY_DRIVER_LAUNCH.md`; the measured
  answer to "usable yet / publishable yet", with the command behind each claim,
  is the internal `READINESS.md`.

## Thesis

Software increasingly comes from machines — generated by LLMs at design time,
synthesized at runtime by autonomous agents. Tests cannot keep up: they sample
the input space, fail to compose, and grow combinatorially with features. Proofs
compose, are context-independent, and give mathematical guarantees.

A compiler that proves the code it compiles is the natural place for this. The
proof becomes a build artifact, not a separate workflow. A compile error and a
proof failure are the same kind of message.

## One program, two languages

The ratified design (the internal two-language spec-surface document and its
companion language-design paper) is one sentence:

> Rust and Lean are two syntaxes for contributing to the **same trust-ir
> module**. That module is verified at the root and compiled into the binary.
> Proofs are about the **literal program objects**, and code and results cross
> the language boundary in both directions.

Two drop-in invariants hold it up. **Vanilla Rust is valid input** — trustc
compiles all valid Rust identically, and unannotated code gets the default safety
obligations. **Vanilla Lean is valid input** — Clean accepts Lean 4 and
machine-imports real `.olean` artifacts.

Everything that follows from that sentence is a consequence, not a separate
feature:

- **Contracts are grammar.** `fn f(..) requires P ensures Q decreases e` is
  signature syntax, sitting where the type sits. Not an attribute, not a macro,
  not a comment convention. There is exactly one place a clause can be written,
  so there is exactly one thing it can mean.
- **Lean enters through a parser island.** `clean { … }` at item position is a
  grammar form vanilla Rust rejects, so no valid program changes meaning. The
  island body is Clean source: rustc keeps only its span and never
  name-resolves, def-collects, or type-checks it.
- **The Clean kernel is the sole trust root.** Every engine's output is
  untrusted; `Certified` means the result was reconstructed and re-checked by the
  kernel. `Solver-Validated`, `Bounded-Checked(N)`, and `Finite-Model-Checked(M)`
  still trust an engine and its bounds — that residual trust is exactly what
  those grade names disclose, and why none of them licenses UB-check elision.
- **Engines are invisible.** ay, trust-wp, trust-mc, trust-vc, ty, clean-auto sit
  behind `trust-router`. Users pick properties, not provers. Each engine's native
  format — SMT-LIB, TLA+, VNN-LIB, RustHorn prophecy, Alethe/LRAT — is
  engine-internal and never a user surface.

Rust and Lean are the only **authoritative** languages for program objects,
specifications, and proofs. TrustJS, TrustPy, and TrustZig admit
JavaScript/TypeScript, Python, and Zig as untrusted, zero-authority frontends:
each must elaborate fail-closed into an inspectable Rust+Lean/trust-ir artifact
with source revision, behavioral reference, corpus, and delta evidence fixed
independently of the proposed translation. Frontend text and inferred intent may
guide a proposal; they cannot assert a proposition, add an unchecked assumption,
or choose the evidence that judges them.

## Architecture

```
     Rust source                                   Lean source
  (clauses in the signature)                    (clean { … } island;
             │                                   .lean files are target)
             ▼                                          │
   typed `trust_contracts` query                        │
   (the single source of truth)                         │
             │                                          ▼
             └────────► trust-spec-elab ────►  clean-elab / Clean kernel
                        (clause → kernel goal)          │
                                  │                     │
                                  ▼                     ▼
                      ═══════ ONE trust-ir Module ═══════
                      producers: trust-thir-lower (Rust/THIR)
                                 clean-compiler (Lean/Clean)
                      carries: functions, Goal obligations,
                               CleanCic / ProofRef / Inherited proofs
                               ┌──────────┴──────────┐
                    obligations│                     │the program
                               ▼                     ▼
                        trust-router              trust-cg  ──►  binary
                   (the ONLY dispatch point)
        ┌─────────┬─────────┬─────────┬─────────┬────────────────┐
        ▼         ▼         ▼         ▼         ▼                ▼
       ay     trust-wp  trust-mc  trust-vc     ty       clean-auto / authored
      (SMT)     (WP)      (BMC)  (proof calc) (temporal)   (tactics / proofs)
        └─────────┴─────────┴─────────┴─────────┴────────────────┘
                               │  engine output is untrusted
                               ▼
                 reconstruction → Clean kernel recheck
                               │
                               ▼
                    multi-axis grade record
        (only Certified × Certified licenses UB-check elision)
```

**Where the implementation actually stands against that picture.** The Rust
producer (`trust-thir-lower`) is live and runs at the `mir_built` hook, but its
capability is deliberately structural: it does not yet bind source contracts,
state epochs, or obligation ownership to trust-ir SSA values, so it has no proof
or native-request authority. An empty direct obligation table means "not wired",
never "verified". Authenticated MIR-derived material (`trust-mir-extract` →
`trust-ir-bridge`) remains the compatibility and differential-evidence lane that
carries real verdicts while that binding, verdict parity, cache rekeying, and
codegen migration finish. MIR is neither the canonical semantics nor the
end-state frontend. LLVM is still the default backend; `trust-cg` requires a
feature-gated build to exist at all (see the capability table below) and is not
selectable from a default-built toolchain.
Its output-preservation gate is enforced rather than aspirational — the backend
decodes the bytes it emitted, computes their machine semantics, and refuses to
write an object whose semantics are refuted against the IR — but it cannot yet
support a verified-codegen *replacement* claim, because the fragment it compiles
is a narrow slice of Rust and the byte-level proof covers a narrower slice still.

**The `trust-cg` fragment**, enforced by hard errors at session validation and
mono-item collection, not by convention: `aarch64`/`x86_64` on the exact audited
built-in triples (`*-apple-darwin`, `*-unknown-linux-gnu`/`-musl`,
`x86_64-pc-windows-msvc`/`-gnu`; `wasm32-unknown-unknown` is analysis-only,
custom JSON targets are rejected); `rlib` as the only linked crate type;
`-Cpanic=abort`; exactly one codegen unit; no debuginfo, LTO, incremental, PGO,
coverage, sanitizers, stack protectors, control-flow mitigations, `-Ctarget-cpu`,
`-Ctarget-feature`, or LLVM pass controls; `extern "Rust"` and non-unwinding
`extern "C"` only, with every argument and the return passing directly in an
integer register (`bool`/`iN`/`uN`, at most 64 bits, no extension, no stack
arguments, no variadics); functions only, so a reachable `static` or `global_asm!`
is refused. The byte-level proof adds its own frontier on top: AArch64 machine
semantics over straight-line integer scalar shapes.

## What is built, what is not

| Capability | State |
|---|---|
| Rust contract clauses (`requires` / `ensures` / `decreases`) | live: parsed into `ast::FnContract`, lowered, and read back through the typed `trust_contracts` query |
| Level 0 safety obligations over supported MIR | live; unproved obligations fail the build under strict verification |
| `clean { … }` parser islands | live: parsed by the real Clean parser, elaborated, kernel-checked; a rejected island fails the Rust build |
| Rust ↔ Clean shared namespace | live for the E6/E9 lanes: a Rust function's defining equation can be imported into the kernel environment, and an uncited `ensures` calling an island definition can discharge by kernel definitional equality |
| Clean kernel recheck of engine output | live for the covered obligation classes; `Certified` is the grade that means it happened |
| A pure `.lean` front door | live in `targo trust check <file.lean>`, which kernel-checks the file in process through the same CIC kernel the islands use, and fails closed on an `axiom`, a `sorry`, or a parse error. `targo trust build` refuses a `.lean` operand rather than let a successful compile read as a discharged proof. **`trustc` still has no Lean input path** — hand it a `.lean` file and it parses it as Rust |
| The Lean → trust-ir producer inside a trustc build | **not built here.** `clean-compiler::emit_trust_ir` exists in the Clean repo; nothing in the Trust compile path calls it, so the shared module currently has one live producer |
| Arbitrary Lean inside an island | **not built.** The island is delimited by a Rust token tree, so it is the Rust-lexable Clean subset: ASCII only, no external `.olean` import, and a `}` inside a Lean comment or string fails closed |
| PROOF / CALL proof-only visibility | **not built.** Specified in the design; no compiler surface yet |
| Direct trust-ir proof authority | **not built.** The direct producer is structural-parity-only; proving still runs through the authenticated MIR-derived lane. The distance is measurable rather than rhetorical: re-measured 2026-07-25 with `scripts/trust_ir_producer_scorecard.py` on a seeded 600-file `tests/ui` sample (default seed, stage2 built from the range-fold miscompilation fix audited internally on 2026-07-25), the direct lane reached 1972 bodies, lowered 1204 (61.1%) with zero unsupported shapes, and the sampled-interpretation differential adjudicated 633 — **632 agreed, 1 diverged**. The earlier figures for this row (2442 bodies, 1406 lowered, 779 agreed / **0** diverged) were taken on `d8a9eb292`, the binary later proven to miscompile, and are superseded: on a correct compiler the lane is *not* divergence-free. The one divergence is `tests/ui/issues/issue-43806.rs::bar` — `fn bar() -> !`, where the THIR producer types the signature `[]->[Never]` and the MIR oracle types it `[]->[]`. That is a seam-modelling disagreement about the uninhabited return rather than a value disagreement, but it is exactly what the differential exists to catch, so the row no longer claims the lane is never wrong where the oracle can look — it claims the lane is less complete (69% of bodies get no equivalence verdict at all) and has one known signature-shape disagreement |
| Direct trust-ir codegen authority (the flip) | live, and narrower than its name. A body whose derived MIR was proven identical to the built MIR is re-derived from trust-ir on the codegen seam. `flip_session_enabled` requires `debuginfo == None` because the Module carries no spans or `var_debug_info`, and targo emits `-C debuginfo=2` for the `dev` profile and no debuginfo flag at all for `release`. Measured on a five-body scalar probe (2026-07-25): **5 flips with no `-C debuginfo` flag and at `=0`, 0 at `=1` and `=2`; 3 at `-C opt-level=3`** — identical before and after the `MatchBranchSimplification` fix, so this row does not inherit that defect. "Compiled from trust-ir" therefore describes a release-shaped build and **never the default `targo trust build`**. The gate is now pinned by `session_gates_allow_flip`'s unit tests rather than by its comment |
| Whole-crate verification with cross-function summaries | partial |
| `trust-strengthen` end-to-end spec inference | partial |
| `trust-backprop` end-to-end source rewriting | partial |
| prove → strengthen → backpropagate convergence on real programs | not yet |
| `trust-cg` verified codegen backend | experimental, and **not present in a default-built toolchain** — the builtin is `#[cfg(feature = "trust-cg")]`-gated (`rustc_interface/src/util.rs`) and `bootstrap.toml` declares no `codegen-backends`, so `-Zcodegen-backend=trust-cg` on a normal `./x.py build` fails with "failed to find a 'codegen-backends' folder in the sysroot". It is also `CrateType::Rlib`-only (`rustc_codegen_trust_cg/src/lib.rs`), so it cannot link an executable. When it *is* built, its emitted objects are gated on a byte-level output-preservation proof over the fragment described above. Measured 2026-07-25: it has never emitted a byte in this checkout |
| `#[trust::verified_codegen]` on the default LLVM lane | live: reports whether trust-cg's emission for this target is proved equal to the function's IR semantics, or that only the structural round-trip check held. It says nothing about the LLVM bytes the build actually ships |
| TrustJS / TrustPy / TrustZig frontends | design/BUILD only; nothing shipped |
| Self-proof (the compiler proving itself) | **not built.** Bootstrap runs with verification explicitly disabled |

## Three ideas

1. **The compiler proves the code.** A verification pass after MIR optimization
   extracts proof obligations and dispatches them to backends. Raw `trustc`, its
   same-sysroot `rustc` alias, and the authenticated primary-crate path that
   `targo trust` sets up verify fail-closed. In that lane a failed required
   obligation has the same product status as a compile error. Bare `targo` is
   not that lane: it is the package manager, and it refuses to compile until the
   invocation says which of the two claims the artifact will carry.

2. **AI infers the strongest spec.** When code carries no contracts, an inference
   layer (abstract domains, CEGIS, LLM-backed proposals) infers the strongest
   preconditions, postconditions, and invariants the code can support. Inference
   does not change the program — it proposes what the program should be held to.

3. **Backpropagation rewrites the program.** When the inferred spec cannot be
   satisfied, the program is wrong or under-specified, and the rewrite layer
   modifies the source to make the proof go through: replacing unchecked
   arithmetic, inserting assertions, tightening types, adding precondition checks
   at callers. Of those, only the additive checks are written without asking:
   a proposed contract clause is an unverified claim and an arithmetic
   replacement is a behavior change, so both are queued for review by default.
   Whatever the loop does write, it writes against a checkpoint and takes back
   when the next prove pass says the frontier got worse.

The three form a loop — **prove → strengthen → backpropagate → re-prove**.
Convergence on real programs is not a completed claim; current reports are
evidence about the proof frontier, not evidence that the loop reached a fixed
point.

## Proof levels

Properties route to the verifier suited to them.

- **Level 0 — Safety.** Panic, overflow, bounds, division-by-zero and related
  obligations over supported MIR. Routed primarily to `ay`, with native typed
  routes for bounded reachability and ownership obligations in development.
- **Level 1 — Functional.** `requires` / `ensures` contracts. The clause surface
  and the elaborator are live; broad semantic discharge of functional contracts
  is in progress.
- **Level 2 — Domain.** Liveness, fairness, linearizability, robustness, protocol
  correctness. Experimental research surface — not a production proof lane.

## Inside the compiler

### The verification pass

`compiler/rustc_mir_transform/src/trust_verify.rs` runs after MIR optimization.
Per crate it first checks every `clean { … }` island into one source-ordered
`CleanIslandSession`, so later islands and later citations see what earlier ones
declared. Then, per `Body<'tcx>`:

1. `trust-mir-extract` walks the MIR into a `VerifiableFunction` (`trust-types`)
   — a rustc-independent representation carrying control flow, types, memory
   operations, and the function's contract clauses as recovered by the
   `trust_contracts` query.

2. `trust-vcgen` generates verification conditions for the supported subset:
   safety obligations (overflow, bounds, casts, division, assertion
   terminators), contract obligations, and developing inter-procedural
   summaries. Loop, unsafe, and functional coverage is still incomplete.

3. `trust-router` dispatches each VC to a backend, memoizing solver results
   in-process by formula hash (`trust-cache`'s `result_cache`, wrapped by
   `solver_cache::SolverCachedRouter`). Nothing is replayed across runs: the
   verify pass deliberately never populates a cross-run proof cache, because a
   per-function content key cannot capture the whole-program facts a Trust
   verdict consumes, so a warm rebuild could replay a stale `Proved` — a false
   PROVE. There is no incremental verification today.
   `trust-certify` re-checks what the kernel can re-check, and
   supplies the E6 admission and E9 citation/defeq lanes that connect a clause
   to an island declaration.

4. Failed obligations can be analyzed by `trust-strengthen`, which proposes
   named preconditions in place.

5. Results are emitted as structured per-function rows on stderr — one
   `TRUST_JSON:{…}` line each — which `targo trust check` decodes.

The iterative `prove → strengthen → backprop` driver is **not** in this pass.
`trust-loop` has no compiler call site — the last one was removed in
`30a681917c`, and the crate is now reachable only from `trust-integration-tests`.
`trust-backprop` is reached from `targo trust loop`, outside the compiler.

Sixteen files under `rustc_mir_transform` carry `// Trust:`-marked edits; the
rest are spread across `rustc_session`, `rustc_parse`, `rustc_monomorphize`,
`rustc_interface`, `rustc_ast_lowering`, `rustc_mir_build`, `rustc_middle`,
`rustc_hir`, `rustc_resolve`, and a dozen more. `rustc_codegen_ssa` and
`rustc_codegen_llvm` carry **none** — proof-carrying metadata does not reach the
LLVM backend today, and any doc that says it does is describing an intention.
Every modification to an upstream file is marked `// Trust:` so upstream merges
stay tractable.

## The crates

57 Trust-owned packages live under `crates/`. Verification backends are separate
repos, pinned as submodules under `first-party/`.

**Foundation** — `trust-types` (core IR + formula arena), `trust-cache`,
`trust-version`, `trust-spec`.

**Producers into trust-ir** — `trust-thir-lower` (Rust/THIR → trust-ir, the
direct producer), `trust-mir-extract` (MIR → `VerifiableFunction`),
`trust-ir-bridge` (the MIR-derived compatibility lane into trust-ir).

**Specification and the Clean lane** — `trust-spec-elab` (clause → kernel goal),
`trust-certify` (island checking, E6 admission, kernel recheck), `trust-clean`
(VC → Clean certificate pipeline), `trust-semantics` (kernel-checked denotations
of the safety predicates), `trust-cert-meter` (the one certification honesty
meter).

**VC generation, dispatch, loop** — `trust-vcgen`, `trust-router`, `trust-loop`,
`trust-convergence`.

**Refinement** — `trust-strengthen` (abstract domains, CEGIS, ICE, Houdini,
LLM-backed proposals), `trust-backprop` (AST rewriting, checked-arithmetic
substitution, assertion insertion, caller propagation).

**Backend bridges** — `trust-bmc` (→ trust-mc), `trust-wp` (→ trust-wp),
`trust-vc-bridge` (→ trust-vc), `trust-cg-bridge` (→ trust-cg LIR),
`trust-ny-bridge` (→ ny neural certificates), `trust-wasm-bridge`

**Temporal** — `trust-temporal` (state-machine extraction), `trust-spec-temporal`

**Analysis and binary lifting** — `trust-symex` (symbolic execution,

**Proof artefacts and reporting** — `trust-proof-cert` (certificates and chain

**TrustJS / TrustTS** — `trust-js-parse`, `trust-js-value`, `trust-js-interp`,

## Milestones

Ordered by dependency.

- **M1 — Build the compiler.** `./x.py build --stage 2` from a Trust seed. The
  repo ships no public prebuilt sysroot; each reviewed checkout builds and
  validates its own, and a build becomes evidence only after current-commit
  provenance, inventory, and acceptance gates pass. *Build path implemented;
  packaged/default-toolchain evidence still needs fresh receipts.*
- **M2 — Prove a function.** Per-function L0 safety plumbing runs in the
  compiler. The example-corpus command produces a regression diagnostic, not
  proof: it records mode, corpus scope, declared terms, compiler exit, and the
  observed compiler digest, but authenticates no source or tool provenance.
  *Implemented for supported MIR; independently authenticated proof receipts
  remain open.*
- **M3 — Prove a crate.** Whole-crate verification with cross-function summaries
  and incremental verification, on real crates with >100 functions.
  *In progress.*
- **M4 — Infer specs.** `trust-strengthen` end-to-end: missing preconditions and
  invariants inferred and surfaced. *Partially landed.*
- **M5 — Close the loop.** `trust-backprop` end-to-end, converging on small but
  real programs. `trust-cg` integration begins. *Not yet.*
- **M6 — Self-proof.** The compiler proves itself, with verification enabled
  during bootstrap. *Not started.*

## Decisions

| Decision | Why |
|---|---|
| Put verification in the compiler, not around it | A proc-macro wrapper can never reach MIR-level invariants or the kernel. |
| Contracts as grammar, not attributes | One place to write a clause is one thing it can mean. Parallel contract systems are how a program and its spec drift apart. |
| Lean as a parser island, not a macro | The body must never be name-resolved or type-checked by rustc. A macro cannot promise that. |
| The Clean kernel as sole trust root | Engines are fast and wrong sometimes. A CIC kernel re-checking the reconstructed term is what `Certified` has to mean. |
| trust-ir as the one module both languages produce | Two producers, one semantics. It is also what makes trust-cg and a Rust-free toolchain reachable. |
| Merge upstream periodically, don't vendor | Stay current with Rust language evolution; keep the drop-in promise testable. |
| Pluggable backends behind one router | Different properties want different solvers. The router decides, the user does not. |
| Backends as sibling repos | Each engine has its own scope, cadence, and contributors. |
| Source rewriting as a first-class step | The loop converges by changing the program *or* the spec, never by lowering the bar. |
| LLVM remains default codegen | `trust-cg` is real but experimental. Adoption does not wait on it. |
| Two authoritative languages, N zero-authority frontends | Rust + Lean own program/spec/proof authority. Everything else elaborates fail-closed and carries independent fidelity evidence. |

## Not in scope

- Treating JavaScript/TypeScript, Python, Zig, their annotations, or inferred
  intent as a third authoritative language or as proof evidence.
- Additional frontend campaigns beyond TrustJS, TrustPy, and TrustZig (Swift,
  C, …). The architecture does not preclude them; none is ruled in.
- A standalone verification framework running outside the compiler. The
  verification pass is the framework.
- A separate proof checker shipped as its own public binary. Kernel recheck is a
  grade the compiler can reach, not a second tool the user runs.
